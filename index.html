Why a separate method

The usual threat modeling questions still work for AI. They just miss the places where AI systems actually break. An AI system is still software, with APIs, data stores and identities, and all of that needs the normal analysis. What changes is the model in the middle.

The model reads its instructions and its data as one stream of text, so any email or web page it reads can give it orders. It doesn't behave the same way twice, which means a safeguard that holds 99 times can fail on the hundredth try. When it calls tools it uses real credentials, and whoever steers it gets those permissions. It can also do damage with nobody attacking it, simply by being confidently wrong.

So I kept the four classic questions from the Threat Modeling Manifesto and rewrote each one around the model.

1Read

What can the model read, and what can it do?

Draw the system. A data flow diagram is still the best tool, with one addition: mark every path where content reaches the model, and every action the model can trigger.

On the way in, list the system prompt, user input, files, retrieved documents, web pages, tool results and anything kept in memory. If someone outside your control can write to it, mark it untrusted. On the way out, list every tool, the permissions it runs with and whose identity it uses.

For agents, also note what runs without approval, what persists between sessions and which tools come from third parties. An MCP server is someone else's code, and its tool descriptions are someone else's prompts. Look for the confused deputy too. That's an agent with broad rights acting for a user with fewer rights, and it can be talked into doing what the user couldn't do alone.

2Fail

How could it be fooled, mistaken or misused?

Go through the diagram one element at a time. Ask how an attacker could steer it, how it could be wrong on its own, and how someone could use it for something it was never meant to do. STRIDE still covers the ordinary parts of the system. For the model I use the OWASP Top 10 for LLM Applications as a prompt list. These come up most often:

ThreatWhat it looks like
Prompt injection LLM01A web page the agent summarizes tells it to send the user's files somewhere.
Data leaks LLM02A broad search pulls another customer's records into an answer.
Excessive agency LLM03An agent with delete rights misreads a request and wipes records.
Poisoned data LLM05Someone plants documents in the knowledge base to steer the answers.
Hidden context exposure LLM08A user pulls out a system prompt that contains an API key.
Unchecked output LLM10Generated text reaches a shell or a browser without validation.
Memory poisoningSomething planted in an agent's memory today steers it next week.
Evasion and driftA sticker fools a vision model, or customer behavior shifts and errors creep up unnoticed.

The agent check

For agents I run one test first. It comes from Meta's Agents Rule of Two and Simon Willison's lethal trifecta. Does it read untrusted input? Can it reach private data? Can it change something or send something out? Three yeses in the same session mean injected text can make it leak data or act against its user. Treat that as high priority until one of the three is gone or a person approves the action.

Ranking

Rank threats the usual way, by likelihood and impact, with one shortcut. Where untrusted content reaches the model, assume injection will work sooner or later. What's left to separate threats is impact, and the grid makes that quick.

3Limit

What limits the harm when it fails?

Assume it will fail, and decide now what stands between that failure and real harm.

The model is not a security boundary.

A line in the system prompt saying "never share customer data" is a request, and the model may ignore it. The real limits go in code, outside the model.

ControlIn practice
Least privilegeScoped credentials, read-only by default. The tool checks permissions, never the model.
Human approvalA person confirms anything irreversible and sees exactly what will run.
Split the riskNo single session gets untrusted input, private data and the power to act.
Output handlingValidate against a schema, parameterize queries, run generated code in a sandbox.
Retrieval accessFilter documents by the user's permissions before they reach the model.
No secrets in promptsAssume the system prompt will leak, and keep keys and credentials out of it.
Caps and logsCap tokens, spend and steps. Log prompts and tool calls, and protect those logs like production data, since they hold everything users typed.

Sometimes the best control is taking something away. An agent that can't send email can't be tricked into sending one.

4Prove

How will we know the limits hold, after every change?

A design review doesn't finish the job. You can't predict a model's behavior from a diagram, so you test it, and then you keep testing.

Turn every serious threat into an adversarial test, including injection through documents, web pages and tool results. Run each test many times, since the output varies, and agree on an acceptable failure rate before you start. For anything that sends data out, that rate should be close to zero. After launch, log actions and have someone actually read the alerts.

Then rerun everything when something changes. Normal software changes behavior when its code changes. An AI system can change with a new model version, an edited prompt or one extra tool, and no code change at all. That's why Prove leads straight back to Read.

Two examples

The same four questions, asked about two very different systems.

Email assistantFraud-scoring model
ReadReads every incoming email, and anyone can send one. Can search the mailbox and send as the user.Reads payment details. Its score approves or blocks payments with no person involved.
